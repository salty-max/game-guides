# Changing core

`packages/core` is the app: its pages, components, stores, styles, the page shell and the build config. Every guide ships it, so a core change reaches all three sites. All three Vercel projects rebuild on it, because their ignore commands watch `packages/core`.

## How core and a guide meet

- **Core reads a guide only through `virtual:guide/…`.** `guide.ts` imports `virtual:guide/config`, `Layout.tsx` and `DashboardPage.tsx` import `virtual:guide/panels`, and `main.tsx` imports `virtual:guide/theme.css`. `vite.ts` aliases `virtual:guide/` to the app's `src/guide/`, and each app's `tsconfig.json` maps the same path for the typechecker. A new file core reads this way must then exist in every guide.
- **A guide reads core only through the subpath exports** in `packages/core/package.json`: `types`, `format`, `fonts`, `guide`, `progress-state`, `store/*`, `sync/*`, `components/*`, `vite`, `icons` and `app.css` (the stylesheet, which Storybook loads). To give guides something new, add an export. There's no barrel file, on purpose.
- **`config.ts` stays at the bottom of the import graph.** A guide's `config.ts`, and the helpers it imports (`run-log.ts`, `estimate.ts`), use only `@hundo/core/types` and `/format`. Core's `guide.ts` imports the config, and the stores import `guide.ts`. A config that reached for a store or a component would close the loop. Panels can use core's stores and components, because nothing in the config imports them.
- **Per-guide saved state** goes in `extra`. A guide declares its type by declaration merging on `"@hundo/core/types"`'s `Register`, as `run-log.ts` and `estimate.ts` do. `GuideConfig.state.extra` then reads and initialises it.

## Saved progress

Readers' progress lives in their browser, so a careless change can wipe it.

- The keys are `<storagePrefix>.v1` for progress (`progress-state.ts`), `<storagePrefix>.theme` for the theme (`store/theme.ts`) and `<storagePrefix>.sync` for a synced device's ledger (`sync/local.ts`). `theme-init.js` reads the theme key before the app loads. Don't change how any key is built. Each guide's `guide.test.ts` pins all three full keys.
- `boot.ts` runs before any store reads storage. It redirects the old hash routes (`#guide/3`). For a guide that moved address (`brand.home` and `brand.movedFrom`), it also hands each reader's progress over from the old address to the new one, through the URL fragment. `boot.test.ts` covers the handover, and [deploying.md](deploying.md#pitfalls) says when to use it. `main.tsx` imports it first, and renders nothing while it's leaving for the new address. Keep that order.
- Saves and backups use one format, `{ version: 3, guide, checks, ceiling, spoilers, chapter, extra }`. `validateState` reads every save on load and every imported backup, and quietly drops checks for ids the data doesn't have.
- To change the format: bump `version` inside the saved object (not the key's `.v1`, which stays forever), keep reading every older version, and write only the new one. Then extend `progress-state.test.ts` and each guide's legacy cases in `guide.test.ts`, the ones that load real older saves. The three guides still read their saves from before the shared format through `config.state.legacy`.

## Keeping storage

By default a browser may clear a site's storage on its own, and progress with it. `persistence.ts` asks it not to with `navigator.storage.persist()`, on the reader's first tick of a visit in that tab (never on load, and never for a tick another tab saved), unless storage is persistent already or the guide asked in the last 30 days. An installed app asks once more if the last ask came from a tab. When and where it last asked is kept under `<storagePrefix>.persist`, as `<ms> tab` or `<ms> app`. It's written before any wait, so two tabs that each tick, or a new visit while a Firefox prompt is still open, don't ask again. Losing or renaming that key only means asking again early, so unlike the other two it may change, but for a Firefox reader who blocked the prompt that's a prompt again. The dashboard's Progress backup panel adds a line when `persisted()` says no, pointing to Export progress and, outside an installed app, to the home screen with the backup imported there. `persistence.test.ts` covers the rules and `App.test.tsx` the tick and the dashboard line.

What each browser does with the request (checked 2026-11-15):

- **Chrome and other Chromium browsers** decide silently: granted if the site looks important to the reader (engagement, installed or bookmarked, notifications allowed), otherwise refused, and asking again later is fine ([web.dev](https://web.dev/articles/persistent-storage)). Without it, storage can be evicted when space runs low ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)).
- **Firefox** asks the reader with a permission prompt, with no click needed first. "Allow" is remembered. "Block" lasts only a while unless they tick "remember", which is why the guide waits 30 days between asks. A private window gets no prompt and a refusal (`PermissionUI.sys.mjs` and `dom/quota/StorageManager.cpp` in [Firefox's source](https://github.com/mozilla-firefox/firefox)).
- **Safari** (17 and later) decides silently, "based on heuristics like whether the website is opened as a Home Screen Web App" ([WebKit, 2023](https://webkit.org/blog/14403/updates-to-storage-policy/)). Safari also deletes a site's script-written storage, localStorage included, after seven days of Safari use without the reader interacting with it. Home-screen web apps keep their own count and aren't expected to lose their data ([WebKit, 2020](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)). The 2023 post says a persistent origin "might be excluded" from eviction, the seven-day kind included. On an iPhone (iOS 18.7, Koholint's live build, 2026-11-15), Safari didn't grant the request in a tab: after a tick, which is when the guide asks, the dashboard still showed the line. Added to the home screen, the guide opened with nothing ticked: the app didn't start with the tab's progress. The line showed in the app on opening too, from `persisted()`, before anything was ticked there. After a tick in the app, which is when the guide asks, the line was gone: the app's storage was persistent once the guide had asked. So on that iPhone the home screen is where the guide's storage became persistent, and the advice the line gives in a tab, to add the guide to the home screen and import the backup there, holds.

## Syncing devices

`src/sync/` keeps one guide's progress the same on a reader's devices, through the API in `services/sync` ([its README](../services/sync/README.md)). Device storage stays the truth and sync only catches up; nothing here runs, or costs a request, until a device is linked.

- **Pairing:** a device shows a six-digit code and another types it (`SyncScreen.tsx`, opened by `{ kind: "sync" }`; `sync/pairing.ts` holds its calls). No account. The server sets a `hundo_sync` cookie that script can't read and a `hundo_link` one it can, and the guide reads only the second, to know it is linked without a request. On hundo.quest the link covers every guide in a browser. Installed phone apps keep their own storage and cookies, so each installed guide takes a code of its own (below).
- **What `hundo_link` and `<prefix>.sync` mean together:** neither, nothing runs. The cookie only, this guide joins the group: it pulls first, then sends what it adds, so linking merges and never replaces (`seed` in `sync/fields.ts` holds the rules). The ledger only, the link is gone (unlinked in another guide, or expired): the ledger is dropped and progress stays. A cookie that names another group than the ledger's means the device moved (it typed a code from a device in one): the old ledger goes and it joins afresh, as for a first link, since an untick stamped in the old group means nothing in the new one.
- **The ledger is the merge model.** `sync/ledger.ts` is byte for byte `services/sync/src/ledger.ts` (`ledger.test.ts` holds them equal; change both together): each key (`c:<rowId>`, `ceiling`, `chapter`, `spoilers`, `x:<path>`) has a stamp, and the later one wins. `sync/fields.ts` flattens a state into keys and lays them back over it. A row id has to be a valid key (`ledger.test.ts` checks every row), and a guide's `extra` goes by leaf: keys of letters, digits, `_` and `-`, at most 60 leaves of at most 256 bytes. A leaf that doesn't fit is left out of sync, not sent.
- **Stamping happens in `store/progress.ts`'s `commit`**, after the save, through `recordLocalChange`, so a change made here is stamped and marked to send. `applySynced` (what sync pulled) and `reloadFromStorage` (what another tab saved) don't stamp, or a pull would be sent straight back. `replaceAll` does, which is why an import replaces progress on every linked device, and the settings say so. The progress is written before the ledger.
- **`sync/cycle.ts` is one round**, under `navigator.locks` so two tabs take turns; `sync/engine.ts`, started by `useSync()` in `App.tsx`, decides when: on opening, 2 seconds after a change (never more than 15 after the first unsent one), as the page hides (a push with `keepalive`), on coming back after 10 seconds or more (`visibilitychange`, and `focus` and a bfcache `pageshow` where those come instead or as well, since an installed iPhone app doesn't always fire the same one), while showing every 20 seconds, backing off by half again each poll that finds nothing (and nothing was changed here) up to 2 minutes and quick again after a change on either side (`pulled` in a round's outcome says the group had something new), never while hidden, and when the browser is back online. After a failure it backs off from 5 seconds to 5 minutes and doesn't poll on top. What polling costs: a poll with nothing to send asks the server whether the guide's data has changed (it sends the revision it last saw), and when it hasn't the answer costs two store commands and nothing is pulled or written on either side. A poll that finds a change, or any full sync, costs six, and eight when the API refreshes the device's last-seen, which only full syncs do, so eight in practice; a push costs ten or eleven, twelve or thirteen with the refresh. The client makes a poll a full sync every ten minutes, and when its daily touch is due. So a guide left open and untouched asks about 33 times an hour, some 100 commands (some 230 before revisions). Against the free plan's 500,000 commands a month (shared by every reader of all three guides): two devices with a guide open 8 hours a day and untouched come to about 50,000, and a pair in steady use all that time, with a tick every three minutes on one or the other, to about 200,000 (an estimate from those rates: some 80 quiet polls, 10 polls that find a change and 10 pushes an hour for each device; some 430,000 to 480,000 before revisions). Because quiet polls leave a device's last-seen alone, the device list can show one that is polling as seen up to about twelve minutes ago, so the Sync screen says "Seen in the last 15 minutes" for any fresher than that. When the quota runs out the API answers 503, and the guides show sync as paused and go on working on their own. The firewall's 120 requests a minute for an address is far off with three devices (9 a minute at the quick pace). Only the server's own `401 unlinked` unlinks a device; a network error, a full store (413), one that is busy or not set up (503) or a limit (429) leaves progress and the ledger as they were.
- **A guide's chapter and ceiling** are held to its own chapter count and never reset to 1, a row this build doesn't know stays in the ledger without being applied, and `viewFrom` moves the open chapter back to the ceiling under spoiler protection as a view, never a stamped change.
- **The theme is deliberately per device.** Devices want different themes ("system" already follows each one's own setting), and `theme-init.js` applies `<prefix>.theme` before first paint, before any network answer exists. Progress, spoiler settings, ceiling and chapter do sync.
- **Tests:** `sync/cycle.test.ts` runs two browsers (their own storage, cookies and addresses, in `test/sync-world.ts`) against the real API handler on an in-memory store, so what the guide sends is what the API accepts. `engine.test.ts` (fake timers), `fields.test.ts`, `local.test.ts`, `SyncScreen.test.tsx` and the stamping cases in `store/progress.test.ts` cover the rest, and each guide's `guide.test.ts` pins its `extra` as keys.
- **The two devices of a pair link a few seconds apart, so each runs follow-up rounds.** The one that types the code joins at once, to a group that has nothing yet; the one that showed it learns of the link from its next status look (every 3 seconds) and only then pushes what it has. So `syncAfterLinking()` in `sync/engine.ts` runs a round at once and again after about 3, 8 and 15 seconds, on both sides (the quiet poll makes each cost two store commands when nothing has arrived), and the new device's screen fills without a reload. Before this, the typing device waited for its next poll: every 5 minutes before the polling change, every 20 to 120 seconds after it. `cycle.test.ts` has the sequence with the real handler.
- **Another device can be removed from the group** (`removeDevice`, the Remove button on every other device's row, behind a confirm; `/api/remove` on the server, which checks the target's own record). The device finds out on its next call (`401 unlinked`) and keeps its own progress; nothing is deleted from the others. The list's ids come from an up-to-date server; an older one's list has none, so no button shows. A device the group hasn't heard from for 60 days is removed by itself the next time its group is read (the quiet poll doesn't read it), records and all: a lost phone that wakes up is unlinked and has to be linked again, and a reinstalled app's old entry goes by hand or after 60 days. A stolen cookie can remove every other device (the README's known limits say so).
- **A device that shows a code links only while its Sync screen is open.** Showing a code again links it if another device typed one meanwhile.
- **A reader's guide gets the new build only when they accept the update prompt** (`registerType: "prompt"`, [deploying.md](deploying.md#pitfalls)). The first real link on 15 Nov 2026 hit it: Brave and the installed iPhone app, open before the deploy, showed no "Sync devices" button in the settings until "Reload" was pressed on "A new version of the guide is ready". Checking a deploy by hand starts with that prompt.
- **On an iPhone, each guide on the Home Screen is a device of its own.** WebKit says a Home Screen app's storage is separate from Safari's once it is added, and the probe saw it copy Safari's cookies once, at that moment. On 15 Nov 2026 the user linked the Koholint app, and the Red Dead app, an app of its own on the same iPhone, wasn't linked, although `rdr.hundo.quest` in Brave was (one link covers every guide in a *browser*). That fits one cookie jar per app. Whether the Red Dead app had taken the update then isn't known, and wouldn't change it, since the link's cookies never reached it. So the Sync screen says it on an Apple device, on the Off and the Linked screens (it says a guide added after linking in Safari should come up linked only to a reader in Safari: whose cookies an app added from another iPhone browser copies is unverified), and an installed app's label carries its guide (`deviceLabel`: "Safari · iPhone · Koholint app", the guide's `brand.shortName`; a label is what the server lists as the device, 40 characters at most, and a guide's name isn't personal data). The label is sent when a device links, and the server changes a device's label only when it is made or moves to another group, so a device linked earlier keeps "… · installed app" until it is unlinked and linked again. The guide's name goes in only on Apple devices: an installed Chromium app on desktop or Android normally shares its browser's cookies (general knowledge, not tried here), so it is one device with the tab, whichever guide linked it, and keeps "· installed app". Which guides a device has synced isn't shown: the server keeps one "last seen" per device, not per guide, and showing it would need a record per device and guide, deleted along with the rest on unlink, forget and expiry, an API change and a deploy. The label tells the same story for the price of none of that.
- **Checked on real devices (15 Nov 2026, production):** Brave on a Mac and the installed Koholint app on an iPhone linked by a typed code and synced both ways, an untick included, and `rdr.hundo.quest` in the same Brave showed "Progress saved · Synced" with no code of its own. The production log showed `pair/start`, `pair/claim` and the syncs as 200. The same day, with the new build, the Red Dead app on that iPhone took a code of its own (the Mac in Brave showed it linked: three devices, "Chrome · Mac", "Safari · iPhone · installed app" for the Koholint app and "Safari · iPhone · RDR app"), a tick made in the app reached the Mac after a reload, and one made on the Mac reached the app after it was swiped away and reopened. The Echoes app wasn't on that iPhone, so it wasn't tried.
- **The chapter is a reading position, and a visit stamps it.** A device sitting on a hidden chapter's page that a pull then reveals records that visit as its own change, and so takes the chapter back from the device that moved on.

## The page shell

- `index.html` is core's, filled in per guide by `vite.ts` from the brand: title, description, theme colour, corners, storage prefix and the `@font-face` rules. In dev, core's plugin serves it for any HTML navigation, so deep links like `/guide/3` work under `pnpm dev`.
- **`theme-init.js` stays an external file.** It sets `data-theme` before the first paint, so the page never flashes the wrong theme. The CSP every guide sends has `script-src 'self'`, which blocks inline scripts. `vite.ts` serves the file in dev and emits it in the build, and the service worker precaches it. `deploy.test.ts` fails if core's `index.html` template gains an inline script, or the CSP allows one. It doesn't see the built page, so after a change to the Vite plugins, check `dist/index.html` for injected scripts too.

## Styles

- Core ships one stylesheet, `app.css`, which `main.tsx` imports. It orders the cascade layers `theme, base, legacy, components, utilities`, loads Tailwind's theme and utilities (no preflight yet), and pulls in `tokens.css` and `styles.css`. A guide only sets the eleven palette colours in its `theme.css`, which loads after it.
- `tokens.css` holds core's design tokens: the colours derived from the palette, the status and category colours, the corner presets and the layout sizes, in the `theme` layer. Its `@theme` blocks hand them to Tailwind as variables (`bg-paper`, `rounded-card`, `font-display`), never as copied values, so a guide's palette and corners reach every utility. Tailwind's own colours, radii, shadows and fonts are cleared: `bg-red-500` doesn't exist.
- `styles.css` is the old house style ([house-style.md](house-style.md)), loaded into the `legacy` layer, and is moving into Tailwind components a few at a time. A token overridden there (`--bar` and `--rail-w` in the small-screen media queries) only wins because `tokens.css` sits in a lower layer: an unlayered rule beats every layer, and so does a rule in a higher one. `theme.test.ts` checks the layer order in `app.css`, how each file is imported, and that every `:root` in `tokens.css` is inside `@layer theme`.
- Tailwind reads class names from core's `.ts` and `.tsx` files only (`@source` in `app.css`), so a utility class in a guide would build to nothing. Lint (`eslint-plugin-better-tailwindcss`, entry point `app.css`) keeps that from happening quietly: in core it rejects unknown, duplicate and conflicting classes and keeps their order, with the classes still defined in `styles.css` allowed until their rules move; in `apps/**/*.tsx` it rejects every class that isn't one of those legacy ones.
- When a component moves to Tailwind, its legacy rules go with it, the contextual ones too (`.group-tools .button`). The `.button` class no longer exists, so those rules would do nothing, and where a leftover rule did match, a utility would beat it on any property both set, whatever the selector's specificity (the `utilities` layer sits above `legacy`). A context becomes a prop (`size="compact"`) or a CSS variable the container sets (`--button-px`); a rule on a property the component's utilities don't set, such as the margin in `.walkthrough-heading>button`, can stay. Class conflicts inside one component (two `border-*` colours) aren't seen by lint when they sit in different strings: give each variant its own, and let a story check the computed colour.
- A class name that is also a Tailwind utility gets that utility's rules in the `utilities` layer, which beats `legacy`. Take care with names built at runtime, which lint can't see: the outline button once carried the class `outline`, and Tailwind's own `.outline` added a 1px outline to it.
- A colour that the contrast test checks has to be a hex value or exactly `color-mix(in srgb,var(--a) N%,var(--b))`, with no spaces after the commas. Anything else makes the theme test throw "not a colour this test can resolve". The test reads `tokens.css`, and also fails if any stylesheet in `packages/core/src` uses a `var(--…)` that neither the palette nor core defines.
- The build now writes an `@supports (color:color-mix(…))` fallback block for each `color-mix()` token, which the build before Tailwind didn't (about 0.7 KB gzipped more CSS per guide). `tailwindcss({ optimize: false })` doesn't change it, and which build pass adds them isn't verified. Every browser the guides support has `color-mix`, so the fallbacks never apply.
- Tailwind's `@tailwindcss/vite` plugin is left out of the jsdom tests, which never process CSS.
- After a style change, check all three guides in the browser. They differ in palette, fonts, corners, layout and the length of their text ([testing.md](testing.md#in-a-browser)).

## Loaded on use

Base UI's popups, with the floating-ui code under them, came to about 56 KB gzipped of every guide's first download. They load on use now, in chunks of their own: the first download is 55.8 KB smaller, and 3.9 KB above where it was before Base UI, which is the sync client that landed since ([the numbers](#what-was-measured)).

- **What is lazy, and why those.** The dialogs (`DialogFrames.tsx`, with every screen in `screen-list.ts`, so the settings and any screen added later) and the select (`select-impl.tsx`). A page can be read without either, and floating-ui comes in with the first popup. Both chunks are listed in `components/chunks.ts`.
- **What stays eager: whatever is always on the page.** Nothing from Base UI is in the entry today: the rows' checkbox (`CheckBox.tsx`) and the chips are plain markup. When a part that is always on the page moves onto Base UI (the row checkbox is planned to), it stays in the entry, and only the popups go in chunks (the next one is the tooltip). That keeps the code every page needs, Base UI's shared helpers included, in the first download, and the floating-ui code out of it.
- **One file per control, once the page shows it.** A module belongs to one chunk, so if the entry imports `controls.tsx` for one checkbox it takes the radio group, the code field and the file field with it. `controls.tsx` is for what the dialog's screens use. A control that a page shows on its own gets its own file, as `Select` did when it left `controls.tsx`.
- **Pages import a shell, never the module behind it.** `DialogHost.tsx` (in `Layout`) and `Select.tsx` import `chunks` and render what it loads; nothing outside `chunks.ts` imports `DialogFrames.tsx` or `select-impl.tsx`, except the dialog's own screens, which use `SelectImpl` directly (a shell inside the chunk would flash its stand-in). One stray static import puts the chunk back in the first download: after a change, check the entry in `dist/assets`.
- **`loadable.ts`, not `React.lazy`.** `loadable(() => import(…))` keeps a module once it has loaded and forgets a failure, so the next ask tries again. `useLoadable` returns the module, or undefined while it's on the way, and re-renders when it arrives. `React.lazy` needs a Suspense and an error boundary, and a lazy component whose import fails (a tab left open across a deploy asking for a file the new build has replaced, or no connection) takes the whole app down when nothing catches it. Here a failure is just a state, and a module that has already loaded renders at once, which is also what lets the tests stay synchronous.
- **When it loads.** `whenIdle` fetches both chunks once the page has loaded and the browser has a moment, so the page's own images and the reader's first taps never compete with them, and not at all for a reader who asked to save data. A select fetches its chunk sooner when the pointer or the focus reaches it. Safari has no `requestIdleCallback` (checked in Playwright's WebKit, the Safari 27.2 engine, where it's undefined; Chromium and Firefox have it), so a one-second timer stands in. The select's chunk is the larger of the two (42.4 KB gzipped against the dialog's 17.6 KB in Koholint's build), because the dialog's settings screen uses the select and the code under both sits in `select-impl`; on every guide both arrive at about the same time, a second or so after the page loads. The service worker precaches every chunk when it installs, so offline use and a tab left open on an old build keep working. What this saves is the first download and its parse, not the bytes a returning reader ends up with.
- **While a chunk is on the way.** The select shows its closed trigger drawn by hand (same size, label, value, so nothing moves). A tap or an arrow key on it is kept: the list opens when the select arrives, and the focus it had goes to the real trigger. A dialog asked for first loads its chunk on the spot and appears when it arrives, without the fade-in, which needs a dialog that was mounted closed. If a chunk the reader asked for can't come, a toast says why ("Reload the page to get the latest version" when online, since the likelier cause is a newer build; "Check your connection" when not), the dialog closes, and the next tap or opening tries again; a failed look-ahead is silent. The toast replaces an undo toast, which lasts seconds.
- **Tests and stories load the chunks first.** `test/setup.ts` loads them in a `beforeAll` (after a test file's own `vi.mock`s are in place, since the dialog's chunk reads the guide), and `.storybook/preview.tsx` in a loader, so a test, and axe, meets the real components. `loading.test.tsx` mocks `chunks` to test what shows before they arrive; a story or test of a new lazy part needs the same two lines.

## Tests

- Core has no test script of its own: it can't run without a guide. Each app's Vitest runs its own `src/**/*.test.*` plus every test under `packages/core/src`, against that guide's config. A new shared test goes in `packages/core/src`, and runs three times.
- A test for one layout only: wrap it in `describe.runIf(config.layout === "article")`, as `App.test.tsx` does.
- **Raw CSS loads empty in Vitest unless it's let through.** `vite.ts` sets `test.css.include` to `/\.css\?raw$/`, so `?raw` imports get their text and any other CSS import gets nothing. Read a stylesheet as text with `?raw`. Before that line existed, the theme test had been passing on an empty string.
- `test.env.GUIDE_ROOT` is the app folder. `deploy.test.ts` uses it to read the app's `vercel.json` and compare it with the other apps'.
- **jsdom is most of what a test file costs, so a file that never touches the DOM opts out.** Start it with `// @vitest-environment node` (`data`, `deploy`, `theme` and `progress-state` do), and the shims in `test/setup.ts` only run where there's a `window`. A file stays on jsdom if it, or anything it imports, reads `localStorage`, `location` or `document`: `boot.ts`, the stores, and so each guide's `guide.test.ts` (it imports `THEME_KEY` from `store/theme`). Under Node 26, `localStorage` in a node file is `undefined` with a warning, not an error, so a store's `try/catch` can hide it.
- **A file that mounts React calls `allowSlowMounts()` (`test/slow.ts`) before its tests.** A mount of the whole app takes 0.1 to 0.4 s on an idle machine, and ten to thirty times that with several checks running at once, which went past Vitest's 5 s default in `App.test.tsx` and `MissablesStrip*.test.tsx` (the first test of `App.test.tsx` took up to 13 s). The helper raises the test timeout to 60 s and Testing Library's `findBy`/`waitFor` wait to 30 s, in those files only. Both just catch a hang. Don't raise them in `vite.ts`.

## Before you commit

- `pnpm check` at the root runs lint, typecheck, tests and build for every package. Each app's typecheck includes core's source, so core is checked against all three real configs. A change to `GuideConfig` or `Brand` fails until every guide follows it.
- Check the change in a browser in at least one article guide (Koholint or Echoes) and Red Dead's checklist layout, on desktop and phone, in light and dark.
- Remember that all three sites deploy from this one change. Check each preview before production ([deploying.md](deploying.md)).
