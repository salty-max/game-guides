# Changing core

`packages/core` is the app: its pages, components, stores, styles, the page shell and the build config. Every guide ships it, so a core change reaches all three sites. All three Vercel projects rebuild on it, because their ignore commands watch `packages/core`.

## How core and a guide meet

- **Core reads a guide only through `virtual:guide/…`.** `guide.ts` imports `virtual:guide/config`, `Layout.tsx` and `DashboardPage.tsx` import `virtual:guide/panels`, and `main.tsx` imports `virtual:guide/theme.css`. `vite.ts` aliases `virtual:guide/` to the app's `src/guide/`, and each app's `tsconfig.json` maps the same path for the typechecker. A new file core reads this way must then exist in every guide.
- **A guide reads core only through the subpath exports** in `packages/core/package.json`: `types`, `format`, `guide`, `progress-state`, `store/*`, `components/*`, `vite` and `icons`. To give guides something new, add an export. There's no barrel file, on purpose.
- **`config.ts` stays at the bottom of the import graph.** A guide's `config.ts`, and the helpers it imports (`run-log.ts`, `estimate.ts`), use only `@hundo/core/types` and `/format`. Core's `guide.ts` imports the config, and the stores import `guide.ts`. A config that reached for a store or a component would close the loop. Panels can use core's stores and components, because nothing in the config imports them.
- **Per-guide saved state** goes in `extra`. A guide declares its type by declaration merging on `"@hundo/core/types"`'s `Register`, as `run-log.ts` and `estimate.ts` do. `GuideConfig.state.extra` then reads and initialises it.

## Saved progress

Readers' progress lives in their browser, so a careless change can wipe it.

- The keys are `<storagePrefix>.v1` for progress (`progress-state.ts`) and `<storagePrefix>.theme` for the theme (`store/theme.ts`). `theme-init.js` reads the theme key before the app loads. Don't change how either key is built. Each guide's `guide.test.ts` pins both full keys.
- `boot.ts` runs before any store reads storage. It redirects the old hash routes (`#guide/3`). For a guide that moved address (`brand.home` and `brand.movedFrom`), it also hands each reader's progress over from the old address to the new one, through the URL fragment. `boot.test.ts` covers the handover, and [deploying.md](deploying.md#pitfalls) says when to use it. `main.tsx` imports it first, and renders nothing while it's leaving for the new address. Keep that order.
- Saves and backups use one format, `{ version: 3, guide, checks, ceiling, spoilers, chapter, extra }`. `validateState` reads every save on load and every imported backup, and quietly drops checks for ids the data doesn't have.
- To change the format: bump `version` inside the saved object (not the key's `.v1`, which stays forever), keep reading every older version, and write only the new one. Then extend `progress-state.test.ts` and each guide's legacy cases in `guide.test.ts`, the ones that load real older saves. The three guides still read their saves from before the shared format through `config.state.legacy`.

## Keeping storage

By default a browser may clear a site's storage on its own, and progress with it. `persistence.ts` asks it not to with `navigator.storage.persist()`, on the reader's first tick of a visit in that tab (never on load, and never for a tick another tab saved), unless storage is persistent already or the guide asked in the last 30 days. An installed app asks once more if the last ask came from a tab. When and where it last asked is kept under `<storagePrefix>.persist`, as `<ms> tab` or `<ms> app`. It's written before any wait, so two tabs that each tick, or a new visit while a Firefox prompt is still open, don't ask again. Losing or renaming that key only means asking again early, so unlike the other two it may change, but for a Firefox reader who blocked the prompt that's a prompt again. The dashboard's Progress backup panel adds a line when `persisted()` says no, pointing to Export progress and, outside an installed app, to the home screen with the backup imported there. `persistence.test.ts` covers the rules and `App.test.tsx` the tick and the dashboard line.

What each browser does with the request (checked 2026-11-15):

- **Chrome and other Chromium browsers** decide silently: granted if the site looks important to the reader (engagement, installed or bookmarked, notifications allowed), otherwise refused, and asking again later is fine ([web.dev](https://web.dev/articles/persistent-storage)). Without it, storage can be evicted when space runs low ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)).
- **Firefox** asks the reader with a permission prompt, with no click needed first. "Allow" is remembered. "Block" lasts only a while unless they tick "remember", which is why the guide waits 30 days between asks. A private window gets no prompt and a refusal (`PermissionUI.sys.mjs` and `dom/quota/StorageManager.cpp` in [Firefox's source](https://github.com/mozilla-firefox/firefox)).
- **Safari** (17 and later) decides silently, "based on heuristics like whether the website is opened as a Home Screen Web App" ([WebKit, 2023](https://webkit.org/blog/14403/updates-to-storage-policy/)). Safari also deletes a site's script-written storage, localStorage included, after seven days of Safari use without the reader interacting with it. Home-screen web apps keep their own count and aren't expected to lose their data ([WebKit, 2020](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)). The 2023 post says a persistent origin "might be excluded" from eviction, the seven-day kind included. On an iPhone (iOS 18.7, Koholint's live build, 2026-11-15), Safari didn't grant the request in a tab: after a tick, which is when the guide asks, the dashboard still showed the line. Added to the home screen, the guide opened with nothing ticked: the app didn't start with the tab's progress. The line showed in the app on opening too, from `persisted()`, before anything was ticked there. After a tick in the app, which is when the guide asks, the line was gone: the app's storage was persistent once the guide had asked. So on that iPhone the home screen is where the guide's storage became persistent, and the advice the line gives in a tab, to add the guide to the home screen and import the backup there, holds.

## The page shell

- `index.html` is core's, filled in per guide by `vite.ts` from the brand: title, description, theme colour, corners, storage prefix and the `@font-face` rules. In dev, core's plugin serves it for any HTML navigation, so deep links like `/guide/3` work under `pnpm dev`.
- **`theme-init.js` stays an external file.** It sets `data-theme` before the first paint, so the page never flashes the wrong theme. The CSP every guide sends has `script-src 'self'`, which blocks inline scripts. `vite.ts` serves the file in dev and emits it in the build, and the service worker precaches it. `deploy.test.ts` fails if core's `index.html` template gains an inline script, or the CSP allows one. It doesn't see the built page, so after a change to the Vite plugins, check `dist/index.html` for injected scripts too.

## Styles

- Core ships one stylesheet, `app.css`, which `main.tsx` imports. It orders the cascade layers `theme, base, legacy, components, utilities`, loads Tailwind's theme and utilities (no preflight yet), and pulls in `tokens.css` and `styles.css`. A guide only sets the eleven palette colours in its `theme.css`, which loads after it.
- `tokens.css` holds core's design tokens: the colours derived from the palette, the status and category colours, the corner presets and the layout sizes, in the `theme` layer. Its `@theme` blocks hand them to Tailwind as variables (`bg-paper`, `rounded-card`, `font-display`), never as copied values, so a guide's palette and corners reach every utility. Tailwind's own colours, radii, shadows and fonts are cleared: `bg-red-500` doesn't exist.
- `styles.css` is the old house style ([house-style.md](house-style.md)), loaded into the `legacy` layer, and is moving into Tailwind components a few at a time. A token overridden there (`--bar` and `--rail-w` in the small-screen media queries) only wins because `tokens.css` sits in a lower layer: an unlayered rule beats every layer, and so does a rule in a higher one. `theme.test.ts` checks the layer order in `app.css`, how each file is imported, and that every `:root` in `tokens.css` is inside `@layer theme`.
- Tailwind reads class names from core's `.tsx` files only (`@source` in `app.css`), so a utility class in a guide would build to nothing. Lint (`eslint-plugin-better-tailwindcss`, entry point `app.css`) keeps that from happening quietly: in core it rejects unknown, duplicate and conflicting classes and keeps their order, with the classes still defined in `styles.css` allowed until their rules move; in `apps/**/*.tsx` it rejects every class that isn't one of those legacy ones.
- A class name that is also a Tailwind utility gets that utility's rules in the `utilities` layer, which beats `legacy`. That's why the outline button's class is `outlined`: a bare `outline` added a 1px outline to every such button.
- A colour that the contrast test checks has to be a hex value or exactly `color-mix(in srgb,var(--a) N%,var(--b))`, with no spaces after the commas. Anything else makes the theme test throw "not a colour this test can resolve". The test reads `tokens.css`, and also fails if any stylesheet in `packages/core/src` uses a `var(--…)` that neither the palette nor core defines.
- The build now writes an `@supports (color:color-mix(…))` fallback block for each `color-mix()` token, which the build before Tailwind didn't (about 0.7 KB gzipped more CSS per guide). `tailwindcss({ optimize: false })` doesn't change it, and which build pass adds them isn't verified. Every browser the guides support has `color-mix`, so the fallbacks never apply.
- Tailwind's `@tailwindcss/vite` plugin is left out of the jsdom tests, which never process CSS.
- After a style change, check all three guides in the browser. They differ in palette, fonts, corners, layout and the length of their text ([testing.md](testing.md#in-a-browser)).

## Tests

- Core has no test script of its own: it can't run without a guide. Each app's Vitest runs its own `src/**/*.test.*` plus every test under `packages/core/src`, against that guide's config. A new shared test goes in `packages/core/src`, and runs three times.
- A test for one layout only: wrap it in `describe.runIf(config.layout === "article")`, as `App.test.tsx` does.
- **Raw CSS loads empty in Vitest unless it's let through.** `vite.ts` sets `test.css.include` to `/\.css\?raw$/`, so `?raw` imports get their text and any other CSS import gets nothing. Read a stylesheet as text with `?raw`. Before that line existed, the theme test had been passing on an empty string.
- `test.env.GUIDE_ROOT` is the app folder. `deploy.test.ts` uses it to read the app's `vercel.json` and compare it with the other apps'.
- **jsdom is most of what a test file costs, so a file that never touches the DOM opts out.** Start it with `// @vitest-environment node` (`data`, `deploy`, `theme` and `progress-state` do), and the shims in `test/setup.ts` only run where there's a `window`. A file stays on jsdom if it, or anything it imports, reads `localStorage`, `location` or `document`: `boot.ts`, the stores, and so each guide's `guide.test.ts` (it imports `THEME_KEY` from `store/theme`). Under Node 26, `localStorage` in a node file is `undefined` with a warning, not an error, so a store's `try/catch` can hide it.
- **A file that mounts React calls `allowSlowMounts()` (`test/slow.ts`) before its tests.** A mount of the whole app takes 0.1 to 0.4 s on an idle machine, and ten to thirty times that with several checks running at once, which went past Vitest's 5 s default in `App.test.tsx` and `MissablesStrip*.test.tsx` (the first test of `App.test.tsx` took up to 13 s). The helper raises the test timeout to 60 s and Testing Library's `findBy`/`waitFor` wait to 30 s, in those files only. Both just catch a hang. Don't raise them in `vite.ts`.

## Before you commit

- `pnpm check` at the root runs lint, typecheck, tests and build for every package. Each app's typecheck includes core's source, so core is checked against all three real configs. A change to `GuideConfig` or `Brand` fails until every guide follows it.
- Check the change in a browser in at least one article guide (Koholint or Echoes) and Red Dead's checklist layout, on desktop and phone, in light and dark.
- Remember that all three sites deploy from this one change. Check each preview before production ([deploying.md](deploying.md)).
